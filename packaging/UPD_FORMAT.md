# CardVault .upd format (schema 1)

`.upd` is a ZIP archive generated by `cardvault.updater.build_package`. It contains `manifest.json` and `payload/<relative application path>` entries. The manifest uses:

```json
{
  "format": "CardVault.Update",
  "schema": 1,
  "product": "CardVault",
  "version": "2.3.0",
  "files": {
    "CardVault.exe": {"size": 123, "sha256": "64 lowercase hexadecimal characters"}
  }
}
```

The example sizes and hash are placeholders. The release builder records real values for every file and produces `CardVault-<version>-Windows-x64.upd`.

Only the application EXE, `_internal/`, `licenses/`, and distribution notices may be updated. User data, the `update` folder and uninstall records are excluded. Relative paths must be canonical Windows-safe paths. Traversal, absolute paths, links, alternate streams, duplicate names, missing payloads, unexpected entries and unsupported identities are rejected. The archive is limited to 20,000 entries and 4 GiB of uncompressed contents.

The UI stages a copy and hashes it without executing it. On update, the app saves tasks and exits. A detached PowerShell helper waits for the owner process, verifies the archive again, extracts and hashes the entire payload, checks EXE version metadata, and only then replaces application files. It backs up original files, records a rollback journal, and attempts restoration if replacement fails. Original backups and an outcome JSON remain inside `update/transaction-*` and `update/update-result.json`. The restarted app keeps its original data-directory argument.

The replacement procedure handles ordinary exceptions and locked files. It is not an atomic whole-directory transaction across power loss. Keep the retained rollback files if recovery is needed. Archive hashes are integrity checks, not proof of publisher identity; no signing key or signature verification is implemented.

## Integration verification

Build the new release, place an original 2.3.2 portable folder at `release/CardVault-2.3.2-Windows-x64`, then run:

```powershell
.\.venv\Scripts\python.exe packaging/test_update.py
```

The test uses fresh isolated copies under `.test-data`, checks successful replacement and restart, then holds an old runtime file open to force rollback. It also checks preservation of task data and unrelated files. It does not install or uninstall software or alter the user's existing installation.

2.2.x applications cannot consume this format. Install 2.3 with Setup first, or use its portable folder. A running 2.3 application accepts only a strictly newer `.upd` version.

## Version-specific delta packages

`build_delta_update.py --base-version 2.3.2` compares complete release folders and emits only changed files. `base_version` and `preserved_files` document the required base and SHA-256 hashes of reused files. Legacy schema-1 updaters ignore these extra fields; the user must select the exact supported base version and a complete installation. The filename includes the base version. This does not remove obsolete libraries. Integration tests verify every changed and preserved file, restart, and rollback with a changed file locked.
